# Protocol contracts

## 1. Transport: loopback HTTP

The app listens on `127.0.0.1` only — nothing is exposed to the LAN. It binds `48321` first and
walks `48321–48330` until it owns a port no other SplitJam instance holds. Three endpoints:

```
GET  /v1/health  -> { "ok": true, "pid": 4321, "instanceId": "<random per launch>",
                      "protocolVersion": 1, "appVersion": "1.4", "buildVersion": "812",
                      "schemaVersion": 2, "startedAt": "2026-11-04T01:00:00Z",
                      "port": 48321, "endpoint": "127.0.0.1:48321",
                      "permission": "edit", "permissionAllowsWrite": true,
                      "permissionAllowsDelete": false }
POST /v1/op      -> request envelope below, Bearer-token authenticated
GET  /v1/export?name=<file> -> raw bytes, Bearer-token authenticated
```

`/v1/health` deliberately needs **no** token: the CLI has to tell "the app is closed" apart from
"the token is stale" before it sends anything, and those need different advice.

The token is generated by the app and shown in Settings → Command Line Access. The CLI stores it
with `splitjam auth` (`0600`) and sends it as `Authorization: Bearer <token>`. Deleting the token
in the app revokes every CLI.

### 1.1 Permission scope (schema 2)

One token, one permission tier, set by the user in **Settings → Command Line Access**:

| `permission` | Allowed | Refused |
| --- | --- | --- |
| `read` | every `*.get` / `*.list` / `*.file` / `*.peaks` / `*.slice`, `ping`, `version`, `capabilities`, `entitlement.*` | every mutating op → `E_FORBIDDEN` (10) |
| `edit` (default) | the above + mixing, beats, sections, chords, lyrics, audio slice export | destructive ops → `E_FORBIDDEN` (10) |
| `own` | everything | — |

`E_FORBIDDEN` is **not** `E_PRO_REQUIRED`: the fix is a settings change, not a purchase. Never
answer it with an upgrade suggestion. `capabilities` returns `permission`, `destructive` and
`allowed` per op, so you can branch before sending a request; `doctor` prints the current tier.
The tier is re-read on every request — a mid-session change takes effect immediately.

Why loopback HTTP and not the old file mailbox: the app-group container is protected by SIP from
macOS 15, so a non-sandboxed CLI cannot read a "port file" or "endpoint.json" there at all. A
loopback server needs zero TCC grants — the same approach Ollama / Chrome DevTools / Figma use.

## 2. Port discovery, done from both sides

| Side | Behaviour |
| --- | --- |
| app | Before binding, `GET /v1/health` on the candidate. If **another** SplitJam answers (`pid`/`instanceId` differ), move to the next port. After binding, probe itself and require the returned `instanceId` to equal the one it just generated — macOS lets two listeners bind the same port under `SO_REUSEADDR`, so "bind succeeded" proves nothing |
| CLI | Probes the whole range concurrently (0.35 s per port), keeps every instance that speaks the health schema, then sends one `ping` with the token to each. Only an instance that **accepts the token** is usable; if several do, the one with the latest `startedAt` wins (the user's action belongs to the window they just opened) |

Pinning: `--port`, `SPLITJAM_PORT` or `auth --port <n>` means **probe only that port** — silently
sliding to a neighbour is the hardest failure to debug. `splitjam auth --port auto` unpins.
`lastPort` is a hint only: the probed range always stays anchored at 48321, otherwise the app
returning to its default port could never be found again.

| Presence | Condition | CLI behaviour |
| --- | --- | --- |
| `running` | a schema-compatible instance answers; token state is reported separately | send the request (token rejected ⇒ `E_AUTH`, exit 9) |
| `incompatible` | SplitJam answers, but only with a schema this CLI does not speak | `E_SCHEMA` (exit 8) |
| `not-ready` | a candidate port is open but nothing answers `/v1/health` | `E_APP_NOT_READY` (exit 3) |
| `not-running` | nothing listens on any candidate port | `E_APP_NOT_RUNNING` (exit 3), **nothing is written** |


## 3. Request envelope

```json
{
  "v": 1,
  "id": "<uuid>",
  "op": "track.gain",
  "params": { "track": "stem:drums", "value": 1.4 },
  "auth": "<token contents>",
  "expectRevision": "7f3a91c2",
  "dryRun": false,
  "deadlineMs": 15000
}
```

`v` newer than the app's schema → `E_SCHEMA` (exit 8): update the CLI. A missing or wrong
`auth` → `E_AUTH`.

## 4. Response envelope

```json
{
  "ok": true,
  "requestId": "<same id>",
  "result": { },
  "error": null,
  "warnings": [],
  "revision": "7f3a91c2",
  "schemaVersion": 1
}
```

On failure `ok=false` and `error` looks like:

```json
{
  "code": "E_PRO_REQUIRED",
  "message": "Multiple practice sections require Pro.",
  "hint": "...",
  "feature": "multiple_sections",
  "reason": "entitlement",
  "upsellTitle": "...",
  "limit": { "free": 3, "used": 3, "remaining": 0, "unit": "sections", "resetsAt": null },
  "appPrompt": "shown",
  "lastSeen": null
}
```

`reason` is only ever `entitlement` or `quota`, and they must be reported differently: the first
needs an upgrade, the second a wait or an upgrade. `appPrompt` is `shown`, `busy`, `deferred`
or `disabled`; `disabled` comes from `--no-app-prompt` or from the user turning prompts off.

## 5. Warnings

```json
{ "code": "W_CLAMPED", "feature": "boosted_stem_volume", "requested": 1.4, "applied": 1.0, "message": "..." }
```

`W_CLAMPED` is the **only** case where the call succeeds but the value was reduced
(gain, speed). It always carries both `requested` and `applied` — without them a script cannot
tell that it did not get what it asked for.

Clamping (gain/speed) and refusing (pitch limits, a 4th section) are different outcomes: the
first writes a smaller value and warns, the second rejects the whole call and writes nothing.

## 6. Revisions

`revision` is a 12-hex-character FNV-1a hash of the record's normalised JSON (`sortedKeys`). No
field is added to `SeparationRecord`. Consequences:

- any field change changes the revision, including changes unrelated to your call;
- identical content always yields the same revision, comparable across processes;
- with `--expect-revision`, a conflict returns `E_CONFLICT_REVISION` (exit 5) and **nothing is
  written**.

## 7. Error codes

| Code | Exit | Meaning |
| --- | --- | --- |
| `E_APP_NOT_RUNNING` | 3 | app closed or quit. **Nothing queued, nothing replayed** |
| `E_APP_NOT_READY` | 3 | a candidate port is open but is not SplitJam (another service, or a half-dead listener) |
| `E_APP_NOT_FOREGROUND` | 3 | needs the app in front (`entitlement.restore`) |
| `E_INVALID_ARG` | 2 | bad argument |
| `E_UNSUPPORTED` | 2 | unknown op, or `implemented: false` |
| `E_MODE` | 2 | refused in the current mode (e.g. BPM in automatic mode) |
| `E_ANCHOR_FAR` | 2 | anchor too far from the nearest beat |
| `E_NOT_FOUND` | 4 | project, track or section not found |
| `E_PROJECT_NOT_OPEN` | 4 | the project must be open in the player |
| `E_ASSET_INVALID` | 4 | missing or corrupt asset |
| `E_MODEL_MISSING` | 4 | model not downloaded (report its size) |
| `E_CONFLICT_REVISION` | 5 | revision conflict |
| `E_PRO_REQUIRED` | 6 | needs Pro — read `reason` to separate entitlement from quota |
| `E_ENTITLEMENT_UNKNOWN` | 6 | purchase state unreadable. **Not the same as "must pay"** |
| `E_AUTH` | 9 (local) | token missing or mismatched |
| `E_SCHEMA` | 8 | protocol version mismatch |
| `E_FORBIDDEN` | 10 | permission tier too narrow — raise Permission in the app, do not suggest upgrading |
| `E_BUSY` / `E_CANCELLED` / `E_LYRICS_SOURCE` / `E_NO_BEAT_GRID` / `E_ENGINE_MISSING` / `E_BUNDLE_STALE` / `E_INTERNAL` | 9 | translate honestly |

`E_TIMEOUT` (exit 7) is produced locally when the app does not answer within `--timeout` —
usually the main thread is busy with separation or export, so retrying later is meaningful.

## 8. Timeouts and cleanup

- every call is a single HTTP request; the client gives up after `--timeout` (default 15 s) and
  reports `E_TIMEOUT` (exit 7). Loopback either answers at once or is not there, so a long wait
  really does mean the main thread is busy separating or exporting;
- if the app quits mid-request the connection drops and the CLI reports `E_APP_NOT_RUNNING`
  instead of waiting out the timeout;
- nothing is queued, spooled or replayed. The app is closed ⇒ the call fails and the project is
  untouched — there is no inbox to accumulate stale writes;
- exports are produced by the app and streamed back over `/v1/export`; the CLI checks the HTTP
  status before writing, then saves to the `--out` path. A failed export never leaves half a WAV
  behind.
