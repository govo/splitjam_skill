# Protocol contracts

## 1. Transport: MCP over loopback HTTP

The app is an **MCP server** (Model Context Protocol), Streamable HTTP transport, JSON-RPC
2.0. It listens on `127.0.0.1` only — nothing is exposed to the LAN — and owns exactly one
port:

```
GET    /health  -> 200, no token. Liveness, versions, permission tier
POST   /mcp     -> JSON-RPC 2.0, Bearer-token authenticated
GET    /mcp     -> 405. This server pushes nothing; there is no SSE stream
DELETE /mcp     -> 204. Session teardown, courtesy only
```

```json
{
  "ok": true, "pid": 4321, "instanceId": "<random per launch>",
  "protocolVersion": "2025-06-18", "schemaVersion": 3,
  "appVersion": "1.5", "buildVersion": "812", "startedAt": "2026-11-05T01:00:00Z",
  "endpoint": "http://127.0.0.1:48321/mcp", "toolCount": 54,
  "permission": "edit", "permissionAllowsWrite": true, "permissionAllowsDelete": false,
  "automationEnabled": true
}
```

`/health` deliberately needs **no** token: a client has to tell "the app is closed" apart
from "the token is stale" before it sends anything, and those need different advice. It
leaks nothing — version, port, permission tier, no project content.

**Why loopback and not a file mailbox**: the app-group container is SIP-protected from
macOS 15, so a non-sandboxed process cannot read an `endpoint.json` or a port file there at
all. A loopback server needs zero TCC grants — the same approach Ollama, Chrome DevTools and
Figma use.

### 1.1 One port, no fallback

The endpoint is written into client configs, so it must be predictable. `48321` is the only
port: if something else holds it, the app **fails** and says so in **Settings → MCP Server**
rather than sliding to a neighbour — a silent move turns into "my client cannot connect"
with no clue. There is no port setting to change; the fix is to free the port and toggle the
server. Before binding, the app probes `/health` and refuses to start if another SplitJam
answers; after binding it probes again and requires its own fresh `instanceId`, because
`SO_REUSEADDR` lets two listeners share a port and "bind succeeded" proves nothing.

## 2. Authentication

One token, generated by the app, shown in **Settings → MCP Server**. Sent as
`Authorization: Bearer <token>` on every `/mcp` request. The token never appears in a query
string: URLs end up in logs, process lists and client config files.

- wrong or missing token → `401` with `WWW-Authenticate: Bearer` and a JSON-RPC error body
  (`code: -32001`);
- turning the server off **deletes** the token, so every configured client stops working —
  that is the revocation path;
- regenerating the token invalidates the previous one immediately;
- the token file is `0600` inside the app's container. Nothing outside can read it, and no
  tool will ever return it.

## 3. Permission scope

One token, one permission tier, set by the user in **Settings → MCP Server**:

| `permission` | UI label | Allowed | Refused |
| --- | --- | --- | --- |
| `read` | Read only | every `*_get` / `*_list` / `*_file` / `*_peaks` / `*_slice`, `ping`, `version`, `schema`, `capabilities`, `entitlement_*` | every mutating tool → `E_FORBIDDEN` |
| `edit` (default) | Edit | the above + mixing, beats, sections, chords, lyrics, slicing | the two destructive tools (delete a section / a chord note) → `E_FORBIDDEN` |
| `own` | Edit + delete | everything | — |

`E_FORBIDDEN` is **not** `E_PRO_REQUIRED`: the fix is a settings change, not a purchase.
Never answer it with an upgrade suggestion. `capabilities` returns `permission`, `mutates`,
`destructive` and `allowed` per op, so you can branch before calling; `/health` and
`scripts/doctor.sh` both print the current tier. The tier is re-read on every request — a
mid-session change takes effect immediately.

## 4. Session

`initialize` returns an `Mcp-Session-Id` header; every later request must send it back.
Sessions live in memory only, so an app restart invalidates them — a client that keeps a
stale id gets `400` with `-32000` and should handshake again. Nothing else is stateful:
there is no queue, no replay, no server-initiated message.

`initialize` negotiates the protocol version: the app speaks `2025-06-18`,
`2025-03-26` and `2024-11-05`, echoes the client's version when it is one of those, and
otherwise answers with the newest. It also returns `serverInfo` (`splitjam`) and an
`instructions` string.

Supported methods: `initialize`, `ping`, `tools/list`, `tools/call`, `logging/setLevel`
(accepted, no-op), `resources/list` + `prompts/list` (empty). Batch arrays are **rejected**
(`400`, `-32700`): the 2025-06-18 revision removed them. Unknown methods get `-32601`.
Notifications (no `id`) get `202` and no body.

## 5. What a tool returns

`tools/call` always returns a normal MCP result — business failures are **not** JSON-RPC
errors, because a transport error hides the code from the model:

```json
{
  "content": [ { "type": "text", "text": "<the envelope JSON, as a string>" } ],
  "isError": true
}
```

The text content is the same envelope, whether the call succeeded or not:

```json
{
  "ok": true,
  "requestId": "…",
  "result": { },
  "error": null,
  "warnings": [],
  "revision": "7f3a91c2",
  "schemaVersion": 3
}
```

On failure `ok=false` and `error` looks like:

```json
{
  "code": "E_PRO_REQUIRED",
  "message": "Multiple practice sections require Pro.",
  "hint": "…",
  "feature": "multiple_sections",
  "reason": "entitlement",
  "upsellTitle": "…",
  "limit": { "free": 3, "used": 3, "remaining": 0, "unit": "sections", "resetsAt": null },
  "appPrompt": "shown",
  "lastSeen": null
}
```

`reason` is only ever `entitlement` or `quota`, and they must be reported differently: the
first needs an upgrade, the second a wait or an upgrade. `appPrompt` is `shown`, `busy`,
`deferred` or `disabled`.

`track_audio_slice` adds a second content block when it succeeds:

```json
{ "type": "audio", "data": "<base64 WAV>", "mimeType": "audio/wav" }
```

Above 8 MB the block is replaced by a text note and nothing is truncated — ask for a shorter
range.

## 6. Warnings

```json
{ "code": "W_CLAMPED", "feature": "boosted_stem_volume", "requested": 1.4, "applied": 1.0, "message": "…" }
```

`W_CLAMPED` is the **only** case where the call succeeds but the value was reduced (gain,
speed). It always carries both `requested` and `applied` — without them nobody can tell that
the call did not get what it asked for.

Clamping (gain/speed) and refusing (pitch limits, a 4th section) are different outcomes: the
first writes a smaller value and warns, the second rejects the whole call and writes
nothing.

## 7. Revisions

`revision` is a 12-hex-character FNV-1a hash of the record's normalised JSON
(`sortedKeys`). No field is added to `SeparationRecord`. Consequences:

- any field change changes the revision, including changes unrelated to your call;
- identical content always yields the same revision, comparable across processes;
- with `expectRevision`, a conflict returns `E_CONFLICT_REVISION` and **nothing is written**.

Every mutating tool also saves an in-app snapshot first, and the result carries
`snapshotId`; `dryRun` results carry `"dryRun": true`.

## 8. Error codes

| Code | Meaning |
| --- | --- |
| `E_INVALID_ARG` | bad or missing argument |
| `E_UNSUPPORTED` | operation not in the catalog, or `implemented: false` |
| `E_MODE` | refused in the current mode (e.g. BPM in automatic mode) |
| `E_ANCHOR_FAR` | anchor too far from the nearest beat; nothing written |
| `E_NOT_FOUND` | project, track, section or note not found |
| `E_PROJECT_NOT_OPEN` | the project must be open in the player |
| `E_ASSET_INVALID` | missing or corrupt asset |
| `E_MODEL_MISSING` | model not downloaded (the message names its size) |
| `E_NO_BEAT_GRID` | no usable grid; run detection in the app or switch to tap mode |
| `E_CONFLICT_REVISION` | revision conflict; `hint` carries the current revision |
| `E_PRO_REQUIRED` | needs Pro — read `reason` to separate entitlement from quota |
| `E_ENTITLEMENT_UNKNOWN` | purchase state unreadable. **Not the same as "must pay"** |
| `E_FORBIDDEN` | permission tier too narrow — raise it in the app, do not suggest upgrading |
| `E_APP_NOT_FOREGROUND` | needs the app in front (`entitlement_restore`) |
| `E_BUSY` / `E_CANCELLED` / `E_SCHEMA` / `E_LYRICS_SOURCE` / `E_ENGINE_MISSING` / `E_BUNDLE_STALE` / `E_INTERNAL` | translate honestly; `E_INTERNAL` means the app log has the detail |

`E_AUTH` and `E_APP_NOT_RUNNING` no longer reach the model: a stale token is a `401` at the
transport, a closed app is a refused connection. Both are reported by the MCP client itself,
which is why the skill tells you what to say for those two cases instead.

## 9. Timeouts and cleanup

- one request, one response, `Connection: close`. There is no keep-alive, no long-poll, no
  server push — a tool call is a question and an answer;
- a slow call means the app's main thread is busy separating or exporting. Retrying while
  it is busy returns `E_BUSY`, not a different result;
- nothing is queued, spooled or replayed. App closed ⇒ the call fails and the project is
  untouched; there is no inbox accumulating stale writes;
- slicing writes the WAV into the app's exports folder and then reads it back for the inline
  audio block; a failed slice never leaves a half file in the envelope.
